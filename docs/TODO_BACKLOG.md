## 1. 安全与账号

- [ ] **忘记/重置密码**。当前用户忘记密码就彻底进不去了。需要单次令牌 + 过期时间，重置后撤销该用户所有旧会话。响应不能泄露邮箱是否已注册。
- [ ] **会话过期与撤销**。`sessions` 表现在只存 token 和创建时间，令牌永不过期、无法批量撤销。至少要加过期时间；改密码时应能一次性踢掉所有设备。
- [ ] **登录限流**。目前对暴力破解没有任何防护。
- [ ] **联系方式加密存储**。微信号/IG/小红书目前是明文列。
- [ ] **服务条款/隐私版本记录**。前端有勾选框但服务端不记录同意了哪个版本、什么时候同意的。

## 2. 校友认证（目前完全是前端假的）

前端有完整的三种认证入口 UI（校友邮箱 / 学信网 / 推荐码），但**后端一个字段都没有**——点了"确认认证"只改浏览器里的状态，刷新后靠前端 `applyBootstrap` 里的兼容逻辑硬撑着。

- [ ] 认证状态与方式落库
- [ ] 校友邮箱：发验证码/验证链接，校验回执
- [ ] 推荐码：签发、核销、一次性约束
- [ ] 学信网：OAuth 回调对接（依赖供应商）
- [ ] 认证过期与重新认证
- [ ] **认证作为推荐的硬门槛**：未认证用户既不该收到推荐，也不该出现在别人的候选池里。现在这条规则只在前端 UI 层面拦，后端 `gale_shapley_matching` 完全没看认证状态。

## 3. 匹配与安全

- [x] ~~**"暂时跳过"目前无实际效果**~~ 已实现：跳过后本周内该推荐降级为灰色卡片（保留姓名，隐藏联系方式），周期滚动后自动恢复，两人仍可能再次匹配。不写入 `dislikes`，不影响对方视角。
- [x] ~~**自我介绍与"对 TA 的期待"之间的文本匹配**~~ 已实现：`backend/text_match.py`，字符 (1,2)-gram TF-IDF + 余弦，纯标准库。你的"期待"对比候选人的"自我介绍"（**有方向性**，两个方向分数不同），按 `TEXT_WEIGHT = 0.4` 混进问卷分里排序。
  - 只影响**排序**，绝不筛人：没写文本的人按问卷原本的位置排，不会被扣分。
  - 权重必须 < 0.5，否则两句自由文本能盖过 24 道题（`test_text_cannot_outvote_the_questionnaire` 钉住这条）。
  - 命中的词写进 `weekly_matches.shared_interests`，接口返回 `sharedInterests`，前端在推荐详情页显示"TA 的自我介绍里提到了你期待的：爬山 / 露营"。跳过后连同联系方式一起隐藏。
  - **局限：纯字面匹配。**"喜欢安静"和"不太爱社交"意思相同但没有共同字符，得分 0。要跨过这层只能上 embedding。
  - 停用词按语料的文档频率自动判定，另有一份中文虚词表——字符 n-gram 会造出跨词边界的碎片（真实池子里"找一"占 31% 的文档、"个喜"18%），不过滤的话推荐理由会显示"你们都提到了：的"。
- [x] ~~**期待的年龄段**（P0）~~ 已实现：`users.birth_date` 存出生日期（不存年龄，否则第二天就是错的），`preferred_age_min/max` 存期待区间，注册和个人资料都有 UI。
  - 是**硬筛选**且**双向**：范围外的人两边都看不到对方。单边区间也生效（只填下限＝上限不限）。
  - **填了区间的人，会筛掉没写出生日期的候选人**——和逐题偏好对待缺失答案的规则一致，明确的要求不因为对方资料不全就被悄悄放弃。UI 里写明了这一点。
  - 已有的 45 个账号都没有出生日期，所以真实用户设区间前，池子里能匹配的只有 demo 账号（seeder 已给它们补上 24–40 岁）。
- [x] ~~**同性匹配**~~ 已实现：`users.orientation`（straight/gay/bisexual）+ `seeking_gender` 决定池子，见 `backend/orientation.py`。
  - 三个**互不重叠**的池子：男↔女（二分图，Gale-Shapley）、男→男、女→女。同性池子的人绝不会被推荐给异性池子的人。
  - 同性池子**不能用 Gale-Shapley**——没有提议方/接收方的划分，这是 stable roommates 问题，和稳定婚姻不同，它**可能根本不存在稳定解**。所以用按分数贪心配对（最大权匹配的 1/2 近似），**不声称稳定性**：理论上可能有两个人互相更想要对方却没配上。
  - 双性恋每轮只选一个池子，所以一个人一次只会收到一个推荐。
  - 改性取向会立刻重新配对（落库时间戳触发，不只靠一次调用——否则并发拿不到锁时这次修改会永远不生效）。
- [ ] **重复推荐冷却期**。同两个人可能连续多周被配到一起。
- [ ] **举报**。前端弹窗里的"内容不当/感觉不真实/其他原因"三个按钮点了什么也不做，只有"确认屏蔽"是真的。需要举报落库和后台处理流程。
- [ ] **解除屏蔽**。`dislikes` 只进不出，且产品上是否允许解除待定。
- [ ] **联系方式访问审计**。谁在什么时候因为哪次推荐看了谁的联系方式。
- [ ] **删除头像**（只有上传，没有删除）。
- [ ] **头像内容校验**。目前只查 `Content-Type` 和大小，没有真正解码验证是不是图片，也没有剥离 EXIF（含 GPS 位置）。

## 4. 问卷

- [ ] **题库/维度定义版本化**。24 道题、5 个阶段、7 个维度的定义现在**同时硬编码在两处**：`backend/questionnaire_config.py` 和 `website/src/app/App.tsx`，靠人工保持同步。应由后端提供带版本的权威定义，前端拉取。
- [ ] **答案与定义版本绑定**。改题目会让历史答案失去意义，已提交的答案和定义都应不可变。
- [ ] **维度得分落库**。现在每次都在前端用 `calcDimensionScore` 现算。
- [ ] **专项题库**（家庭关系/育儿观念/金钱与财务/亲密关系）。前端已有"即将开放"的占位 UI。

## 5. 每周四晚 8 点定点揭晓（用户明确要过的需求）

当前是**惰性 7 天滚动**：不看星期几，只在有人发请求时才检查"距上次配对是否超过 7 天"，且算完立刻可见。要改成定点揭晓需要：

- [ ] 真正的定时任务（进程内 APScheduler 或平台的 cron），周四 20:00 触发全量配对
- [ ] "已生成但未揭晓"状态——`weekly_matches` 需要一个揭晓时间字段，`/api/match/current` 按它过滤
- [ ] 未到点时前端显示什么（倒计时？还是完全不显示）
- [ ] 时区确定（北京时间 / UTC / 用户本地）

## 7. 已知的规模问题

- [x] ~~**同性取向无法处理**~~ 已解决：拆成独立池子，同性池子改用贪心配对。代价是同性池子没有稳定性保证（见上）。
- [ ] **非二元性别**。`gender` 仍然只有 男/女 两个值，池子的划分也建立在这上面。非二元用户依然无处可去；这需要重新设计池子的定义，不是加一个枚举值能解决的。
- [ ] **同性池子人太少**。真实用户里目前一个同性取向的都没有，池子全靠 demo 账号撑着。池子小 → 贪心配对的质量下降得比二分图快，且落单概率高。
- [ ] **落单问题**。当前 3 男 6 女，每轮必然 3 人配不到；叠加永久屏蔽后会更严重。需要设计"本周无推荐"的体面呈现，或调整策略。
